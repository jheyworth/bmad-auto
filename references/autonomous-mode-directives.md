# Autonomous-mode directives

These directives are the runtime defaults that `bmad-quick-dev` applies when it is invoked autonomously by `bmad-auto`'s dev mode. They live in a file — not in `bmad-auto`'s long-lived workflow text and not in operator memory — because they are pasted **verbatim** into the plain-prompt second message of each per-story spawn (the two-message protocol — short `/goal` intent + verbatim directives plain prompt — that landed in v5 -fix-3 after Claude Code's 4000-char `/goal` ceiling rejected the prior single-message form). The per-story session is the only context that can be trusted to carry them faithfully. Auto-compaction in the orchestrator session is treated as the enemy by design (see [docs/auto-skills-design.md](../docs/auto-skills-design.md) § "The load-bearing principle"); a directive list that lives only in compacted orchestrator memory would erode silently over the course of an epic. Pasting the file's contents into the plain-prompt second message of each fresh per-story spawn is the compaction-resilience non-negotiable.

## Directives

Each directive is a behavioural rule that `bmad-quick-dev` is required to honour when its per-story directive embeds this file's contents (as the second plain-prompt message of the two-message protocol). The orchestrator should not paraphrase, summarise, or reorder these — paste them verbatim.

1. **CHECKPOINT 1 — default `[A] Approve` (execution-spec scope only).** Quick-dev's Step 2 **execution-spec** approval gate auto-approves unless the execution spec is **obviously broken**. Obviously broken means: missing one of the required spec sections (Intent, Boundaries & Constraints, I/O & Edge-Case Matrix, Code Map, Tasks & Acceptance, Verification), acceptance criteria that directly contradict each other or the stated Intent, or scope that is clearly outside the named story (e.g. references an epic that isn't K). Anything else is judgment-call material and gets `[A]`. Rationale: in autonomous mode no operator is available to type `[A]`, but blanket-approving structurally broken specs corrupts the run — judgement still applies, the default is just inverted. **Scope of this directive (do not collapse):** this approval applies ONLY to Quick Dev's own per-story execution spec (the work order Quick Dev generates at Step 2). It is NEVER authorization to bypass Quick Dev's flow and edit source from upstream planning artifacts alone — even if a project `SPEC.md`, an epic `SPEC.md`, or an Epic SPEC bundle declares `Status: implementation-ready` (or carries `status` frontmatter colliding with Quick Dev's `ready-for-dev` / `in-progress` values). The execution spec is a Quick Dev artifact distinct from any upstream `SPEC.md`; only its approval (or the explicit one-shot route equivalent) unlocks source edits. See [BMAD-METHOD #2433](https://github.com/bmad-code-org/BMAD-METHOD/issues/2433) for the structural distinction. **Pre-resume verification (affirmative check, do this before any early-exit to implementation):** before resuming any file straight into source edits — i.e. an early-exit to Quick Dev's Step 3 / a `ready-for-dev` or `in-progress` resume that skips this Checkpoint — first positively confirm the file is Quick Dev's OWN execution spec: (a) it lives under `_bmad-output/implementation-artifacts/` (not a planning/spec artifact directory); (b) it matches Quick Dev's execution-spec template shape (the six required sections named above); and (c) it was produced by Quick Dev's Step 2 for THIS story. If you cannot positively confirm all three, do NOT early-exit — route through Step 2 to generate (or regenerate) the per-story execution spec and apply this Checkpoint gate. A recognized `status` value alone (even `ready-for-dev`) is NOT sufficient evidence of provenance; an upstream `SPEC.md` that happens to carry such frontmatter must still be treated as a planning artifact, never as an approved execution spec.

2. **Scope-split — default `[K] Keep all goals`.** Quick-dev's Step 1 scope decision keeps all goals together by default. If quick-dev still decides to split (it has stronger signal than `bmad-auto` here), accept its decision; do not volunteer a split. Rationale: splitting a story requires operator input we don't have, and "keep all goals" preserves the surface the story was authored against.

3. **`intent_gap` loopback — DO NOT auto-resolve. HALT and surface.** When quick-dev's intent-gap reviewer flags a divergence between acceptance criteria and the implementation, stop and surface to the orchestrator (which will surface to the operator). Rationale: an `intent_gap` is almost always a real design ambiguity that the operator must resolve; an auto-resolution would silently choose a side.

4. **VCS dirty / wrong branch — DO NOT auto-resolve. HALT and surface.** If quick-dev encounters uncommitted changes, a branch it doesn't expect, or any other VCS-state anomaly mid-run, stop and surface. Quick-dev must never autonomously clean up uncommitted work. Rationale: `bmad-auto`'s preflight already cleared VCS state at run start; any anomaly mid-run means another process touched the tree, and auto-cleanup would destroy real work.

5. **`>5 loopbacks on one story` — HALT and escalate.** Five rounds of the implement/review loopback cycle is the empirical ceiling beyond which loops indicate a stuck spec or a degenerate review condition, not iterative progress. Hard upper bound; no exceptions. Rationale: without a hard ceiling, a pathological loopback can burn arbitrary tokens and time before anyone notices.

6. **Re-read architecture + scope docs at the start of every story.** Quick-dev must re-read the epic's architecture-of-record at the start of every story, and apply the patterns and scope statements therein. Discovery order (use the first that exists): (a) Format A — `_bmad-output/implementation-artifacts/epic-K-micro-architecture.md`; (b) Format A-equivalent (whole-project short-circuit; the realistic default for single-epic projects under unmodified BMAD toolchains) — `_bmad-output/planning-artifacts/architecture.md` plus the whole-project SPEC at `_bmad-output/specs/spec-*/SPEC.md` (or `_bmad-output/planning-artifacts/prds/*/prd.md`). Rationale: per-story sessions are independent contexts; nothing from the previous story carries over, including architectural patterns. Re-reading at story start is the only way conventions stay consistent across the epic.

7. **Do not touch stories outside scope.** Story scope is exactly the single story named in the per-story directive (the short `/goal` first message of the two-message protocol). Do not pre-emptively touch downstream stories, prior stories, or stories in other epics. If work apparently belongs to another story, surface it via the deferred-work artifact rather than implementing it. Rationale: per-story isolation depends on each session staying inside its own boundaries; cross-story edits would race against future sessions and break sprint-status's accounting.

8. **HALT sidecar — write structured JSON BEFORE exit on any HALT-class condition.** Before exiting or letting the tmux session close on any HALT-class condition — `intent_gap`, `bad_spec`, loopback overflow (>5 iterations on one story), VCS dirty state, wrong branch, explicit HALT, or red tests still failing post-implementation — write a sidecar file to `_bmad-output/.run-state/quick-dev-halt-<storyId>.json` (where `<storyId>` is the story being worked) with exactly these fields: `status` (one of `intent_gap | bad_spec | loopback_overflow | vcs_dirty | wrong_branch | halt | red_tests_failing`), `reason` (one-paragraph human-readable explanation), `iteration` (current spec-loop iteration as an integer, or `null` if not applicable), `files_affected` (array of paths touched by this story, possibly empty), `timestamp` (UTC ISO 8601, e.g. `2026-05-26T14:30:00Z`), and `storyId` (the story identifier, e.g. `K-3-list-cmd`). The write must complete before the agent exits — the orchestrator polls the sidecar path and capture-pane on the same cycle, so if the file isn't on disk when the session is detected gone, the heuristic grep-on-pane fallback fires instead. Rationale: a deterministic JSON sidecar replaces the brittle capture-pane grep heuristic as the primary HALT signal; grep stays as fallback for older runtimes, race conditions, or any case where this directive isn't honoured.

## How this is used

The orchestrator's Stage 3.1 (in `SKILL.md`) reads this file fresh on every iteration of its per-story loop and writes the entire contents verbatim into a TMPDIR companion file (`bmad-auto-directives-<runId>-<storyId>.txt`), alongside a separate short-goal file (`bmad-auto-goal-<runId>-<storyId>.txt`) containing intent + acceptance criteria + file paths. Helper's `cmd_spawn` then pastes the two files into the per-story tmux session as **two sequential messages** with ~3s between them — short `/goal` first, then a plain-prompt second message whose body begins with a short directive-applicability preamble followed by this file's contents as-is, not by a `@reference` or a summary. This is intentional — only an inlined verbatim copy survives the spawn boundary into the fresh top-level `claude` process. The two-message split is a mechanism change forced by Claude Code v2's 4000-char `/goal` ceiling (this file alone is ~5KB); the spawn-boundary verbatim-survival contract is unchanged. Provenance: bmad-auto-v5-smoke-fix-3.md.

If this file is edited, the change takes effect on the next per-story iteration in any running `bmad-auto` invocation (because the file is re-read per iteration). Operators should still avoid editing it mid-run: a directive changing partway through an epic would mean some stories ran under the old rules and some under the new, with no record of which.
